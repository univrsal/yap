# Client scripting

Lua scripts that run inside the client: react to messages and people, add
`/commands`, change what is shown or sent, keep time, call out to the web. This
note is why it is built the way it is. What it does, for people who write scripts,
is in [../Scripting.md](../Scripting.md); the examples are in
[../examples/scripts](../examples/scripts).

It is built (it began as seven steps, listed at the end). What has only been
compiled, not run, is under [Open](#open).

## In one picture

	                      ┌─────────────── runtime (one per client) ───────────────┐
	conn (net thread) ──► │ event sink ─► deliver ─► Script (own Lua state) ─► host │
	  filter hook ◄─────► │   on_incoming (mutex)        │ time-sliced tasks   calls │
	  command queue ◄──── │ yap.send, ...  ◄─────────────┘   timers, store, http     │
	UI / headless ──────► │ step, commands, on_send, catalog (items, config)        │
	                      └─────────────────────────────────────────────────────────┘

A **Runtime** owns the **scripts** the user has (the catalog, `items.odin`) and the
ones that are running (each a **Script**: a Lua state, its tasks, timers, store,
settings and pending web requests). Connections are **attached** to it. It is made
at start (UI and headless), stepped once per frame (or per `client_step`), and
holds a mutex while it runs Lua.

## What it starts from

- **`conn` already has a seam.** The network side never touches the UI; the UI
  never touches a `Server_Conn` but through its command queue, and state goes up
  through the `View`. Scripts are a third consumer of the same two directions:
  events out of `conn` (`conn/events.odin`), commands into it (`Chat_Command`, and
  the notices of `view_notice`).
- **Threads differ by target.** Natively `client_step` is on a network thread; on
  the web and when headless it runs in the main loop. A design that needs a thread
  would not build for the web, so none does.
- **Lua is not free everywhere.** `vendor:lua` has prebuilt libraries only for
  Linux amd64 and Windows. So Lua is built from source for every target, wasm
  included, and `vendor:lua` is not used at all.
- **There is a headless client** with its own command line; scripts run there
  too, which makes them a second way to write a bot, one that needs no token.

## Architecture

### Lua is only touched from C

Lua reports errors, yields and the time limit with `longjmp`. If that unwinds an
Odin frame nothing is cleaned up there, and in a web build emscripten emulates
`longjmp` with exceptions through frames it didn't compile. So **the Lua API is
only called from `yap_lua.c`**, and Odin sees status codes: `spawn_chunk`,
`spawn_global`, `spawn_ref`, `resume`, `register`. What a script calls (`yap.*`)
goes through one C function (`api_call`) that turns the Lua arguments into plain
values, calls the host, and turns the answer back; an error the host reports is
raised afterwards, from C. Values cross as `yap_value` trees: nil, booleans,
numbers, strings, lists, maps, and (as arguments only) functions kept as registry
references. Tables are read in two passes (count, then fill, with limits: 8 deep,
4096 values, only names or only `1..n` as keys), so nothing can fail half-way.

### Scheduling: time slices everywhere

A script that loops must not freeze the client, and a web build has no thread to
put it on, so the same scheme is used on every target:

- Each handler call is a **task**: a coroutine. A count hook fires every 1000
  instructions, asks Odin (`hook_check`) what to do, and either continues, yields,
  or raises "script ran too long".
- `step` gives each task turns of 0.5 ms (`TASK_SLICE`) until the frame's budget
  (2 ms in all) is spent; what is left goes on in the next frame. A handler can
  pause itself with `coroutine.yield()`, which means "go on next frame".
- A run has **200 ms of running time in all** (`Limits.total`), then it is killed.
  After the kill the hook runs after *every* instruction, so a script that catches
  the error with `pcall` and carries on is stopped again at once.
- A script's own top-level code is a task too, and is run to the end when it starts
  (waiting at most a second), so that its handlers exist when the first event comes.
- Memory is counted in the allocator: 16 MiB per script; allocating past it fails
  like running out of memory, which is an error in the handler.
- Making a task can itself run out of memory, so it is a protected call and an error
  value, never an abort.

What the scheme can't stop: one C call that takes long (a pattern that backtracks a
lot; `table.sort` of a million entries) never reaches the hook, and a coroutine that
the *script* makes can't be suspended (it would yield to the script, which didn't
ask), so a loop in one runs to the 200 ms and is killed then. `string.rep` results
and patterns are length-limited by wrappers around the library. The backtracking
case needs a step counter inside Lua's matcher, i.e. patching the fetched source; it
is left because it takes a script written to do it.

### Threads and the lock

The Lua state belongs to one thread at a time. `Runtime.mutex` is held by the step,
by the UI's calls (`runtime_set_enabled`, `runtime_run_command`, ...) and by the
filter the network thread asks for. Nothing waits on the lock for long: the network
thread tries for 5 ms (`FILTER_WAIT`) and shows the message as it is if it can't
have it, so a deadlock isn't possible. On wasm there is one thread, so the lock is
taken or not at once: **there is no `time.sleep` on wasm** (WASI's `poll_oneoff` is
not defined, and the web build failed to link when a wait was written there).

Headless reads commands on a stdin thread, so command lines and `/say` are queued
(`runtime_queue_command`, `runtime_queue_say`) for the thread that steps.

### Events and actions

`conn` has one optional `Event_Sink` per connection (`Server_Conn.events`). Where the
UI is told something (`message_arrived`, the account update, `set_state` reaching
`Done`, `publish_status`), `event_*` copies it into the sink (strings owned, at most
1000 kept) under a mutex. The runtime drains it in `step` and calls the handlers of
the scripts that run for that server. The network thread never calls into Lua for an
event.

Actions are the host calls of `yap.*`, checked, and carried out as the user's own
requests would be: `yap.send` is a `Chat_Command` with a channel name (so the channel
being looked at doesn't change); `yap.status` a `view_notice` (the status area at the
top of the chat window); `yap.notify` a desktop notification, which the runtime queues
and the UI shows on the next frame with its own `notice()`, the one it uses for
mentions, DMs and calls (tray icon, or the browser's notifications, or a request for
the window's attention), at most 10 in 10 seconds per script; without a UI (headless)
both are lines in the log. A script has no power those don't have. Text posted with `yap.send` is sent **as typed**, so `@username` in
it is a mention.

### Which servers a script runs for

A script runs for **a set of servers the user chose**: all, or only those listed
(addresses as the client has them, or server keys in hex; possibly none). The script
can't widen it. An event from a server outside it is never delivered, and costs
nothing.

- Every event carries `server = {key, address}`, taken from the connection.
- **An action has a server.** `yap.send("general", ...)` is ambiguous when two
  servers have `#general`, so inside a handler the action is for the server of the
  event; a timer or a web request remembers the server it was made for; anything else
  names one (third argument), which has to be in scope.
- One Lua state serves all of a script's servers. A script that keeps per-server data
  keys it by `ev.server.key`.

### Catalog, approval and config

The runtime knows every script it can find, running or not (`Item`): found as `*.lua`
in `<config>/yap/scripts/` on a desktop, or in the browser's storage under an index.
Each has what it says about itself (`Info`) and what the user chose, kept in
`scripts/config.json`: whether it runs, the permissions approved, the servers, and
**the hash of the text that was approved**. A script whose file has changed since is
not started and says so until it is switched on again, which approves the new text. A
config written by hand without a hash is not tied to a text (a script under
development keeps running as it is edited).

Nothing runs unless it is switched on, and switching on shows what it asks for
(`send`, `notify`, `net`). Reading messages needs no permission, which is why the
page says to switch on only what you trust. There is no signing.

### `get_info` and settings

A script describes itself with `get_info()`, which returns a table. It is read in a
**separate Lua state in which every `yap.*` function does nothing** (so the script's
own top-level code, which usually registers commands, runs without effect), and then
`get_info` is called with a 100 ms limit. The table is untrusted: `parse_info` bounds
every length and count, requires unique keys and a known type, makes the default fit
the type, and leaves out and reports what is wrong, without stopping the script.

Settings are `bool`, `int`, `number`, `string` (`secret`, `max_length`) and `choice`.
`setting_value` is the single place a value is checked (clamped, whole, one of the
choices, cut at a character boundary), whoever sets it. Values are kept in
`scripts/data/<file>.settings.json`; a script reads them with `yap.setting`, gets them
all in `on_load` and a change in `on_setting`. `secret` only hides the value on the
page; the file has it as typed.

### Commands

`yap.register_command(name, [help,] fn)` takes a function, which the host keeps as a
registry reference (an argument the host keeps is marked; the rest are released after
the call, also when it fails). Typing `/name args` in a composer runs it instead of
posting, if a script that runs for the server has it; anything else, an unknown
`/word` included, is a message. Completion lists the commands while the first word is
typed, the palette lists them as "Run /name", and the headless client tries a `/word`
none of its own commands know. Built-in commands win over a script's.

### Filters

Two handlers change things on their way and answer by what they return (nothing or
`true`: leave; `false`: stop; a string: use this instead):

- **`on_send`** runs on the UI thread in `composer_send`, after the check for a
  command and before mentions are encoded. Stopping keeps the text in the box and
  shows a notice. Headless queues `/say` for the stepping thread.
- **`on_incoming`** runs on the network thread, where a message becomes what the UI
  shows (`conn/filter.odin`, `filter_message`, at the points a `Msg` is made from a
  wire message: arrival, a page of history, a thread root, an edit). It changes only
  this client's view; `on_message` still gets the original. A stopped message is shown
  as **`[hidden by a script]`**: the timeline is a window of messages by id, kept in
  step with the server's pages and unread counts, so a message can't just disappear.
  It makes no sound and no notification (it still counts as unread). Search, pins and
  bookmarks show messages as they are. A replacement is plain text.

Neither can be suspended (the answer is needed now), so they run to the end
(`call_sync`) with a **2 ms** limit. A filter that errors, overruns or yields is a
strike; three in a row switch that script's filters off until it is reloaded, and a
good call clears the count.

### Web requests

`yap.http_get/post(url, fn[, options])` need `net`. The request is made while the
script goes on; the answer comes to `fn` later, in a handler of its own, as
`{ok, status, body, headers}` or `{ok = false, error}` (a 404 is `ok`: it means the
server answered). The script keeps `fn`; completions are delivered at the start of a
step, never inside a host call.

- **Limits**: `http:`/`https:` only (also after a redirect); a body 256 KiB; an answer
  1 MiB, then the transfer is stopped; 4 requests out and 30 a minute per script;
  headers are tokens and values without line breaks (so none can be injected), and not
  `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Upgrade`, `TE` or
  `Expect`; timeout 10 s, at most 30. Requests still out when a script goes are
  cancelled. Local and private addresses are allowed, since checking an address is easy
  to get wrong (DNS) and the permission is the guard.
- **Native**: `deps/thirdparty/tinyrequests` (WinHTTP, CFNetwork, or a libcurl loaded
  with `dlopen`), polled from the step; it makes no thread and nothing waits. The
  library is **altered** (marked in its header): `tr_config.max_response_size`,
  enforced in `tr__append_bytes`, the one function all backends collect an answer
  with, and, for libcurl, only http/https also after a redirect and at most 5
  redirects. It also fixes a bug in its WinHTTP URL parser, which read a URL with a
  port (`http://host:8080/`) as port 0 and a host one character short, so on Windows
  every such request failed with "name not resolved" (found by the tests on a Windows
  runner, since they all use a port). Without a libcurl `tr_client_create` fails; the client logs it once, the
  Scripts page and `/script` say so, `yap.http_available()` is false, and a request is
  still answered, at once, with `ok = false`.
- **Web**: the page's `fetch` (`web/http.js`): no cookies, no referrer, redirects
  followed, a timeout, and the size counted while the answer is read. It answers
  through an exported function, noted there and given to the script by the next step.
  Only servers that allow requests from a page (CORS) can be asked, and an https page
  can't ask for http.

### The sandbox

Scripts get the language and `string`, `table`, `math`, `utf8`, `coroutine`; not `io`,
`os`, `package`, `debug`, `dofile`, `loadfile`, `print`, `string.dump`; `load` takes
text only; `collectgarbage` only `count` and `collect`. That is for mistakes and for
limiting what a script can reach. It is not why a script is safe to run: an approved
script reads its servers' messages and, with the permissions, posts and uses the web as
the user.

## Decisions

| | Question | Outcome |
| --- | --- | --- |
| D1 | Vendor Lua source or `vendor:lua` | Source, built as one file for every target; `vendor:lua` is not used. The release has no `onelua.c`, so `yap_lua.c` lists the files |
| D2 | Lua version | 5.4.8 (integers, `utf8`) |
| D3 | May scripts stop or change messages | Yes: `on_incoming`/`on_send`, synchronous, 2 ms, no yielding. A stopped incoming message is a placeholder, not removed |
| D4 | One state per script or shared | One per script: isolation, per-script limits, reloading one |
| D5 | Web requests in a browser | Allowed, always asynchronous, size and time capped; CORS applies |
| D6 | Scripts in the headless client | Yes, same package, driven by its loop; `/script` instead of the page |
| D7 | Share names with bot slash commands | Intended, not done: bot slash commands don't exist yet |
| D8 | Trust for scripts from elsewhere | Permissions shown when switched on; approval tied to the text's hash; no signing |
| D9 | A thread for scripts | None: time slicing in the loop on every target, so one code path |
| D10 | Local/private addresses for web requests | Allowed, with the `net` permission; no allow-list |
| D11 | HTTP backend | tinyrequests natively (altered; libcurl optional on Linux), `fetch` on the web |
| D12 | Script metadata | `get_info()` read in a state where `yap.*` does nothing (not "raises": scripts register commands at the top level); validated by the host |
| D13 | Who chooses the servers | The user, per script; the page writes addresses, the config also accepts keys; may be none |
| D14 | A script's hint of its servers | `servers` in `get_info` is parsed but not used by anything yet |
| D15 | Lua state per server | Shared in v1 (below) |

### A per-server instance mode (not built)

A script could opt in with `per_server = true` in `get_info` and get one Lua state per
(script, server): every instance sees one server and has its own globals and store, so
a script written with one server in mind runs on several. Nothing rules it out: a
script's state is one struct the runtime owns a list of, so it would change how
instances are made and how events are routed to them.

## Testing

`odin test src/client/script` (also in CI) covers: the sandbox, the kill and the
`pcall` evasion, coroutines, memory limits and leaks; tables in both directions; every
`yap.*` function and argument error; timers, the store, commands; both filters, the
strikes, the lock that can't be had, a filter between the steps of a suspended handler;
`parse_info` and every setting type; discovery, approval, the changed-text rule,
settings and their events, scope (including none), add/remove/reload; web requests
through a fake transport, **for real through libcurl to an HTTP server the test
starts** (answers, a 404, redirects, a POST with headers, an oversized answer, a
redirect to `file://`, a refused connection, a timeout), and without a client. Every
example script is loaded from its file and exercised, and a test loads every Lua block
in `docs/Scripting.md` and runs its quick start. `node tools/test_web_http.mjs` tests
`web/http.js` against a server of its own (in CI).

The headless client was run against a live server for events, commands, `on_send`,
settings, a restart, a changed script, and web requests.

Lessons that cost something, for the next change here:

- **A type-check isn't a link.** `odin check -target:wasi_wasm32` passed while the web
  build didn't link (a `time.sleep`); build `web/build.sh` after touching shared code.
- **A test server must not trust its client.** One that handles a connection at a time
  and waits for it to speak hangs when a client opens a connection it never uses (as
  CFNetwork can); each connection gets a thread and a receive timeout, and stopping
  closes the listening socket as well as waking it. Time-based test loops count
  elapsed time, not sleeps: a sleep is 15 ms on Windows.
- **A test that only logs can't fail.** Handlers the runtime runs log their errors; a
  test of a handler's result runs it with `step` and asserts on the results.
- **microui knows a checkbox by the address of its `bool`.** Locals share one, so each
  gets its own id (`mu.push_id`).
- **`defer` doesn't change a named result** that `return` has already set; assign
  explicitly.

## Open

- **The Scripts page has only been compiled**, not seen: layout, the approval step, the
  add form and the text boxes need a look on a display. (Two bugs were found by using
  it: shared checkbox ids, and "all servers" unticking back.)
- **WinHTTP and CFNetwork** are only exercised by the CI runners for Windows and macOS
  (the tests make real requests); nobody has run them by hand. The size cap relies on the
  function they share, and the redirect restriction exists only for libcurl (the other
  two speak only http and https). The first Windows run found a parser bug in the
  library (above), so more may be there.
- **A browser** has not been used; node's `fetch` stood in, without CORS.
- **`on_incoming` was not seen rewriting or hiding a live message.** Its hook was seen
  called in the real message path, and the rest is tested; but in the dev VM a client
  often got no live messages at all (with or without scripts, and before them), so a
  live demonstration failed for a reason of the VM's.
- **Not there**: `yap.reply`, `yap.react`, `yap.channels/users/me`, sending to a direct
  message or a group (`ev.channel` is empty there and `yap.send` addresses channels by
  name), drawing, voice; noticing that a file changed (press Reload); the server's
  *name* in `ev.server` (reading it from the network thread's data needs the event to
  carry it); `get_info`'s `servers` hint; an `on_unload`.
- **Hidden messages still count as unread**, and search, pins and bookmarks show the
  original text.
- **The history decoding failure** seen in the dev VM (a channel with messages makes
  the client log "the server sent a page of messages we can't read" and drop later live
  messages) happens without scripts, in the commit before them too, and was not
  investigated.

## How it was built

Seven steps, each its own commit: (1) Lua built for every target, sandboxed and
time-sliced; (2) events, the `yap` API, the runtime and the server scope; (3)
`/commands`; (4) `on_incoming`/`on_send`; (5) `get_info`, settings, approval, reload and
the Scripts page; (6) web requests; (7) the reference and the examples. The plan that
guided them, and what came out differently, is in this file's history.
